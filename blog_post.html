What Is a Transformer, Really?

Let's forget the jargon for a second. Read this sentence: "The cat sat on the mat because it was tired."

When you hit the word "it," your brain just knows it means "the cat," not "the mat." You don't even think about it. Your brain automatically pays attention to the right words based on context.

That's basically what a Transformer does. For every word in a sentence, it figures out which other words matter most for understanding it. The whole trick comes down to one word: attention.

Before Transformers showed up in 2017 (that famous "Attention Is All You Need" paper — great title, honestly), language models had to read words one-by-one, left to right. Imagine reading with a tiny flashlight that only illuminates one word at a time. Transformers tossed that flashlight and turned on the floodlights — the model sees the whole sentence at once and decides what to focus on.

🍕 Pizza analogy: Think of older models (RNNs) as eating a pizza one bite at a time in order — you can't taste slice 5 until you've finished slices 1-4. A Transformer is like looking at the entire pizza, deciding which slices look best, and eating them in any order. Way more efficient.

The Attention Mechanism: The Secret Sauce

Okay, so this is the part that actually made things click for me. The attention mechanism is basically a tiny search engine running inside the model.

Each word in a sentence asks three questions:

  • Query (Q): "What kind of information am I looking for?" — like typing a search query into Google.
  • Key (K): "What kind of information do I have?" — like the title/tags on a web page.
  • Value (V): "Here's my actual content." — like the actual content on that web page.

When the model processes the word "it" in our cat sentence, the Query for "it" is something like "I need to know what noun I'm referring to." The Key for "cat" is basically advertising "I'm an animate noun, a subject." The dot product between these two vectors is high — it's a match! — so "it" pays a lot of attention to "cat."

A Tiny Concrete Example

Let me make this super concrete. Imagine each word has a tiny 3-number vector (in reality it's 32 or 128 numbers, but bear with me):

# Imagine these are learned vectors (3 dimensions for simplicity)
Token "cat" → Query = [0.5, 0.1, 0.8]   # "I'm looking for subjects"
Token "sat" → Key   = [0.1, 0.9, 0.2]   # "I'm a verb"
Token "it"  → Key   = [0.6, 0.2, 0.7]   # "I'm a pronoun/subject"

# Attention score = dot product of Query and Key
score(cat → sat) = 0.5×0.1 + 0.1×0.9 + 0.8×0.2 = 0.30  # Low match
score(cat → it)  = 0.5×0.6 + 0.1×0.2 + 0.8×0.7 = 0.88  # High match!

See that? "Cat" naturally pays way more attention to "it" (0.88) than to "sat" (0.30). And here's the beautiful part — the model learns these vectors during training. Nobody hand-codes the rules. It just figures out which words should match up.

After computing these scores, it runs them through softmax (basically squashes the numbers into percentages that add up to 100%), then uses those percentages to blend the Value vectors together. So each word ends up with a new representation that's a weighted mix of the words it cared about. Pretty slick, right?

🤔 Why divide by √d? There's one more detail: the scores are divided by the square root of the vector dimension before softmax. Without this, the dot products can get really large, and softmax would essentially say "pay 100% attention to one word, 0% to everything else." The scaling keeps things smooth so the model can attend to multiple words at once.

Multi-Head Attention: Looking at Things from Different Angles

Now here's where things get even cooler. Instead of running one big attention computation, my model splits it into 4 separate "heads" that all run in parallel.

Why bother? Because language is complicated and one attention pattern isn't enough. One head might learn to track subjects ("who's doing the action?"). Another might figure out adjective-noun pairs. A third could focus on nearby words. It's like having four people read the same sentence, each looking for different things, then pooling their notes at the end.

Here's the actual code from my model that does this:

class CausalSelfAttention(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.n_heads = cfg.n_heads           # 4 attention heads
        self.d_head = cfg.d_model // cfg.n_heads  # 128/4 = 32 dims per head

        # One matrix that produces Q, K, V all at once (efficient!)
        self.qkv_proj = nn.Linear(cfg.d_model, 3 * cfg.d_model, bias=False)
        self.out_proj = nn.Linear(cfg.d_model, cfg.d_model, bias=False)

    def forward(self, x):
        B, T, C = x.shape
        # Compute Q, K, V in a single matrix multiply
        qkv = self.qkv_proj(x)              # (B, T, 3*C)
        q, k, v = qkv.chunk(3, dim=-1)      # Split into Q, K, V

        # Reshape: split each into 4 heads of 32 dims
        q = q.view(B, T, self.n_heads, self.d_head).transpose(1, 2)
        k = k.view(B, T, self.n_heads, self.d_head).transpose(1, 2)
        v = v.view(B, T, self.n_heads, self.d_head).transpose(1, 2)

        # The magic formula: Attention(Q,K,V) = softmax(QK^T / √d) × V
        scale = math.sqrt(self.d_head)
        attn = (q @ k.transpose(-2, -1)) / scale  # Score matrix
        attn = attn.masked_fill(self.causal_mask[:T, :T], float("-inf"))
        attn = F.softmax(attn, dim=-1)       # Normalize to probabilities
        out = attn @ v                        # Weighted sum of values
        ...

I remember staring at this code and thinking: wait, this is the revolutionary idea that powers ChatGPT? A dot product, a mask, a softmax, and a matrix multiply? That's it? Yep. That's it. That's the whole magic trick.

The Full Architecture: How It All Fits Together

Alright, time to zoom out. My model is what's called a decoder-only transformer — same family as GPT-2, GPT-3, and LLaMA. Don't let the name intimidate you. "Decoder-only" just means it reads left to right and predicts the next word. That's all.

Here's what the full data flow looks like:

Input: "Once upon a time" → Token IDs [42, 100, 7, 303] │ ▼ ┌──────────────────────┐ │ Token Embedding │ Look up a 128-dim vector for each word │ + Position Embed │ Add "where am I in the sentence?" info └──────────┬───────────┘ │ │ × 4 Transformer Blocks ┌──────────▼───────────┐ │ LayerNorm │ │ Multi-Head Attn │ Each word gathers context from past words │ + Skip Connection │ ├───────────────────────┤ │ LayerNorm │ │ Feed-Forward (MLP) │ Each word "thinks" about its context │ + Skip Connection │ └──────────┬───────────┘ │ ┌──────────▼───────────┐ │ Final LayerNorm │ │ Linear → 4000 logits│ Score for every word in vocabulary └──────────────────────┘ │ ▼ Output: probability distribution over next word

A few things I want to call out here:

  • Token Embeddings — basically a big lookup table. Each of our 4,000 vocabulary words gets its own 128-number vector. These get learned during training.
  • Positional Embeddings — this one tripped me up at first. Since the Transformer sees all words at once (not one-by-one), without position info "cat sat mat" and "mat sat cat" would look identical. Positions fix that.
  • Skip Connections (the "+" arrows) — honestly one of the cleverest ideas in deep learning. They let information flow straight through, so each block only needs to learn a small "correction." Without these, deep networks are basically impossible to train.
  • Feed-Forward Network — expands each word's 128-dim vector to 512 dimensions, runs it through a nonlinear function (GELU), then squishes it back to 128. A lot of the model's "knowledge" lives here.

Training: Watching a Model Learn

Training a language model is one of those things that's conceptually simple but took me a while to really get. The idea: show it a bunch of text, ask it to predict the next word, tell it how wrong it was, nudge the parameters to be less wrong. Do that a few hundred thousand times and hope for the best.

Here's what the core loop looks like, stripped down:

for step in range(max_steps):
    input_ids, target_ids = get_batch()      # Grab a chunk of text

    _, loss = model(input_ids, targets=target_ids)  # Forward pass
    # loss = how surprised the model is by the actual next word

    optimizer.zero_grad()   # Clear old gradients
    loss.backward()         # Backprop: compute gradients
    optimizer.step()        # Update all 1.3M parameters

Every single step, the model sees 16 sequences of 128 tokens each (that's 2,048 tokens per step). Over 500 steps, it processes about 1 million tokens total.

Under the Hood: Key Code Explained

I want to show you a few pieces of the code that made me go "ohhhh, that's how it works."

The Heart of the Model

The SmallGPT class ties everything together. What surprised me is how clean it is:

class SmallGPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        # Step 1: Convert token IDs → vectors
        self.token_emb = nn.Embedding(cfg.vocab_size, cfg.d_model)
        # Step 2: Add position information
        self.pos_emb = LearnedPositionalEmbedding(cfg.max_seq_len, cfg.d_model)
        # Step 3: Stack transformer blocks
        self.blocks = nn.ModuleList([
            TransformerBlock(cfg) for _ in range(cfg.n_layers)  # 4 blocks
        ])
        # Step 4: Final projection to vocabulary
        self.ln_f = nn.LayerNorm(cfg.d_model)
        self.lm_head = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)
        # Neat trick: share weights between embedding and output
        self.lm_head.weight = self.token_emb.weight

That last line — weight tying — blew my mind a little. The token embedding converts words→vectors, and the output layer converts vectors→word-scores. They're doing opposite things, so you'd think they need separate weights. But it turns out sharing them saves ~500K parameters and actually makes the model work better. GPT-2 does this too. When I first read about it I thought it was a hack, but the more I think about it the more it makes sense.

The Causal Mask: No Cheating Allowed

This one's fun. During training, the model sees the full sentence at once — but we can't let it cheat by peeking at future words it hasn't "generated" yet. So how do you prevent a model from looking ahead? A triangular mask:

# Create a mask where True = "block this position"
mask = torch.triu(torch.ones(seq_len, seq_len), diagonal=1).bool()

# Visualized for seq_len=4:
#   Position:     0      1      2      3
# Word 0:   [  OK    BLOCK  BLOCK  BLOCK ]  ← can only see itself
# Word 1:   [  OK     OK    BLOCK  BLOCK ]  ← sees words 0,1
# Word 2:   [  OK     OK     OK    BLOCK ]  ← sees words 0,1,2
# Word 3:   [  OK     OK     OK     OK   ]  ← sees everything

Those masked positions get set to negative infinity before softmax, which makes them exactly 0% attention. Information only flows from past to present — never the other direction. At first I thought this was a weird trick, but it's actually really elegant when you sit with it for a minute.

Learning Rate Warmup + Cosine Decay

Before this project, I figured learning rate was just... a number you set and forget. Nope. It turns out the schedule matters a lot — maybe more than the actual value. Here's what I used:

def get_lr(step, cfg):
    # Phase 1: Warmup (steps 0-50) — start gentle
    if step < cfg.warmup_steps:
        return cfg.learning_rate * (step / cfg.warmup_steps)

    # Phase 2: Cosine decay (steps 50-500) — gradually slow down
    progress = (step - cfg.warmup_steps) / (cfg.max_steps - cfg.warmup_steps)
    min_lr = cfg.learning_rate * 0.1  # Never go below 10% of peak
    return min_lr + 0.5 * (cfg.learning_rate - min_lr) * (1 + math.cos(math.pi * progress))

Think of it like driving: you ease onto the highway (warmup), cruise at full speed (peak learning rate), then gradually slow down as you approach your exit (cosine decay). I tried skipping the warmup once — just went straight to the full learning rate — and the loss went completely haywire. Lesson learned.

Lessons I Learned Along the Way

This project taught me a bunch of things I really didn't expect. Some of these might seem obvious in hindsight, but they hit different when you discover them by breaking stuff.

1. Transformers are simpler than I thought. Seriously. I spent weeks being intimidated before I actually looked at the code. The core idea — Q, K, V attention — is just dot products and softmax. That's it. The genius isn't in any single piece; it's in how the simple pieces stack together.

2. Data > model size. My model's biggest problem wasn't having only 1.3M parameters — it was the tiny dataset. Even a small model can produce decent output if you feed it enough diverse data. GPT-3 isn't magic; it's just very, very well-fed.

3. Tokenization is half the battle and I almost overlooked it entirely. Before text even reaches the model, the BPE tokenizer chops it into sub-word tokens. How well those tokens capture meaningful chunks of language has a massive impact on everything downstream.

4. Loss numbers make no intuitive sense at first. Going from 8.0 to 4.0 sounds like "cutting the error in half." In reality it means going from "random guessing" to "can narrow things down to about 57 plausible words." The log scale took me embarrassingly long to internalize.

5. Don't skip the learning rate warmup. Ask me how I know. (I skipped it. The loss exploded. Fun times.) The warmup + cosine decay schedule that everyone uses isn't some ritual — it's actually critical for stable training.

6. Weight tying is one of those ideas that seems wrong until it's obviously right. Sharing weights between the embedding layer and the output layer saves ~500K parameters AND improves performance. The intuition clicked for me when I realized: words that are similar should have similar embeddings AND similar output probabilities. Of course they should share weights.

💡 My #1 tip if you're just starting: Don't try to understand everything before you start coding. Just build it, run it, watch the loss go down. Then go back and read the code more carefully. I promise it'll make 10x more sense after you've seen it work.

Once it's running, here are some fun experiments to try:
